1. What is this Project? (The Big Picture)

This project is a software-based digital logic circuit simulator. Think of it as a virtual lab where you can build and test circuits made of logic gates — just like the ones used inside computers, phones, calculators — but entirely in software. No physical breadboards, no wires, no risk of burning components.

🎯 One-Line Summary: You draw a circuit using logic gates (AND, OR, NOT, XOR, etc.), connect them with virtual wires, give inputs (0s and 1s), and the simulator tells you what the output will be — and proves it with a truth table.

What Can It Do?

FeatureWhat it means
Build any circuitConnect gates freely using a directed graph internally
Detect feedback loopsAutomatically finds illegal cycles using Tarjan's DFS
Evaluate gates in orderUses Kahn's algorithm to find the correct evaluation sequence
Truth table generationTests all 2ᴺ input combinations and shows outputs
Web GUIDrag-and-drop gate editor in browser, live wire colors
Novel algorithmsLPE (parallel staging) + ISP (fast re-simulation) — original contributions

Who Uses Such Tools in Real Life?

Companies like Intel, Qualcomm, and Samsung use similar (but much larger) software called EDA tools (Electronic Design Automation) to design chips before manufacturing them. Our simulator is a simplified educational version of the same concept.

2. The Problem We're Solving

Real-World Pain Points

When students or engineers design digital circuits on a physical breadboard, they face:

ProblemImpact
Wire clutter & loose connectionsCircuit doesn't work but finding the bug takes hours
Burnt IC chipsWrong wiring = ₹200-500 chip gone
No automated verificationMust manually check all input combinations
No cycle detectionFeedback loops cause unstable oscillating outputs
Slow iterationRe-wiring takes 20 minutes; simulator takes 2 seconds
Building circuits on a breadboard without a simulator is like writing code without a compiler — you only know something's wrong when it explodes (literally).

Our Solution — A Graph-Based Simulator

We model the circuit as a Directed Acyclic Graph (DAG):

  • Each gate = a node (vertex) in the graph
  • Each wire = a directed edge from output of one gate to input of another
  • Signal flows in one direction: INPUT → Logic Gates → OUTPUT
INPUT A ──────┬───────────► [ XOR Gate ] ──────► OUTPUT Sum │ ▲ │ │ INPUT B ───┴────────────────────┤ │ └───────────► [ AND Gate ] ──────► OUTPUT Carry

Using graph algorithms, we can:

  1. Detect if any illegal loop exists (feedback = unstable circuit)
  2. Find the correct order to evaluate gates (topological sort)
  3. Propagate signals from inputs to outputs automatically
  4. Generate exhaustive truth tables for verification

3. How the Simulator Works — Step by Step

When you load a circuit and click "Simulate", here's exactly what happens internally:

  • 1
    Circuit is stored as a graph. Every gate is a node with an ID. Every wire is a directed edge: from_gate → to_gate. We use an adjacency list (like a list of neighbors) for fast traversal.
  • 2
    Cycle Detection (Tarjan's DFS). Before doing anything, we check: "Is there an illegal feedback loop?" We run a Depth-First Search. If we ever reach a node we're currently visiting (gray node), that's a cycle → ERROR reported. No simulation runs on a broken circuit.
  • 3
    Topological Sort (Kahn's BFS). We figure out the correct evaluation order. A gate can only be evaluated AFTER all its input gates are done. Kahn's algorithm finds this order using in-degree counting.
  • 4
    Signal Propagation. We go through gates in topological order. For each gate, we read its inputs, apply its logic function (AND/OR/NOT/XOR/etc.), compute its output, and pass that value to connected downstream gates.
  • 5
    Read Outputs. After all gates are evaluated, OUTPUT gates hold the final result. Display it to the user.
  • 6
    Truth Table. Repeat steps 4-5 for every possible combination of 0s and 1s across all INPUT gates (2ᴺ rows total). Each row is one test case.
Key Insight: A digital circuit is just a DAG. Evaluating it correctly = topological sort. Verifying it = running the simulation 2ᴺ times with different inputs.

5. Algorithms from Literature (Surveyed Papers)

5.1 — Kahn's Topological Sort (1962)

Paper: Kahn, A.B. (1962). "Topological Sorting of Large Networks." Communications of the ACM.

What it does: Given a DAG, produce a linear ordering of all nodes such that every node appears BEFORE the nodes it points to.

Imagine scheduling tasks where task B cannot start until task A finishes. Kahn's algorithm tells you the right order to schedule all tasks so no one waits unnecessarily.

Pseudocode:

1. Compute in-degree for every node
2. Add all nodes with in-degree = 0 to Queue
3. While Queue is not empty:
   a. Pop node U from Queue
   b. Add U to result order
   c. For each neighbor V of U:
        - Decrement in-degree of V by 1
        - If in-degree of V == 0, add V to Queue
4. If result has all V nodes → valid topo order
   Else → cycle detected (should not reach here after Tarjan's check)

Complexity: O(V + E) — visits every vertex and edge exactly once.

Used in our project: Determines the order in which gates are evaluated during simulation.

Drawback (why we extended it): Gives only a flat linear order. Doesn't tell you WHICH gates can run simultaneously in parallel. Doesn't compute how many sequential stages are needed (Critical Path).

5.2 — Tarjan's DFS Cycle Detection (1972)

Paper: Tarjan, R.E. (1972). "Depth-First Search and Linear Graph Algorithms." SIAM Journal on Computing.

What it does: Detects whether a directed graph contains any cycle (loop) using Depth-First Search with 3 colors for nodes.

The 3-Color System:

ColorMeaning
⬜ White (0)Not visited yet
🔲 Gray (1)Currently being visited (on the DFS stack)
⬛ Black (2)Fully processed — all descendants explored

Cycle detection rule: If during DFS we find an edge from a Gray node to another Gray node → we've gone back to a node we're currently processing = cycle!

Imagine exploring a maze. Gray rooms = rooms you're currently inside (doors open). If you walk into a room that's already open (gray), you've found a loop.

Complexity: O(V + E)

Used in our project: Runs before any simulation. If a cycle is found, simulation is blocked and an error is shown.

Drawback: Only detects cycles. Gives no information about parallel execution or incremental updates.

5.3 — Tarjan's Disjoint Set Union / Union-Find (1975)

Paper: Tarjan, R.E. (1975). "Efficiency of a Good But Not Linear Set Union Algorithm." Journal of the ACM.

What it does: Groups elements into sets. Supports two operations: find(x) — which set does x belong to? union(x, y) — merge the sets of x and y.

Imagine you have groups of students. Each group has a leader. find() tells you who the leader of your group is. union() merges two groups under one leader.

Optimizations:

  • Path Compression: When finding root, flatten the path — all nodes point directly to root after first find
  • Union by Rank: Always attach the smaller tree under the larger tree's root

Complexity: O(α(n)) per operation — α is the inverse Ackermann function, essentially O(1) for all practical inputs.

Used in our project: Groups all wires that are electrically connected into "nets". Two wires in the same net carry the same signal value.

Drawback: Static grouping only. Doesn't handle dynamic changes to the circuit topology during simulation.

6. ⭐ Novel Algorithm 1 — Levelized Parallel Evaluation (LPE)

⭐ Original Contribution

Levelized Parallel Evaluation (LPE)

File: NovelAlgorithms.h | Menu Option: 15 | Complexity: O(V + E)

What Problem Does LPE Solve?

Kahn's algorithm gives you a list like: "evaluate gate 0, then gate 1, then gate 2, then gate 3..." — a flat linear sequence. But this is wasteful! Look at the Half Adder:

INPUT A ──► XOR Gate ──► Sum Output INPUT B ──► AND Gate ──► Carry Output

After both inputs are ready, the XOR gate and AND gate have nothing to do with each other. They could evaluate at the same time (in parallel)! But Kahn's forces them into a sequence: XOR first, then AND (or vice versa).

What LPE adds: Groups gates into "stages" where all gates in a stage are fully independent of each other and CAN run simultaneously. Also computes the Critical Path — the minimum number of stages needed to get the final output.

Simple Explanation (In Plain English)

Think of it like a factory assembly line. Instead of one worker doing everything one step at a time, you organize workers into shifts (stages). Everyone in the same shift can work simultaneously because they don't need each other's results. LPE figures out these shifts automatically.

How It Works — Step by Step

  • 1
    Start like Kahn's BFS. Find all gates with in-degree = 0 (gates that don't need any input from other gates — these are INPUT gates). These go into Stage 0.
  • 2
    Assign a level to each gate. Each gate's level = 1 + the maximum level of all its input gates. This is the key difference from Kahn's — we propagate the maximum depth forward.
  • 3
    Group gates by level. All gates at level 0 → Stage 0. All gates at level 1 → Stage 1. Etc.
  • 4
    Compute Critical Path Length. The highest level number + 1 = how many stages you need at minimum to get output. This is the Critical Path.
  • 5
    Compute Parallel Speedup. Total gates ÷ Critical Path Length = theoretical speedup ratio compared to sequential evaluation.

Example — Half Adder

Gate A (INPUT)   → Level 0   ┐
Gate B (INPUT)   → Level 0   ┘ Stage 0 (run simultaneously)

Gate XOR1        → Level 1   ┐ (needs A and B → both level 0, so XOR1 = 0+1 = 1)
Gate AND1        → Level 1   ┘ Stage 1 (run simultaneously)

Gate Sum (OUT)   → Level 2   ┐ (needs XOR1 → level 1, so Sum = 1+1 = 2)
Gate Carry (OUT) → Level 2   ┘ Stage 2 (run simultaneously)

Critical Path Length = 3 stages
Sequential would take 6 steps → Parallel needs only 3 → 2x Speedup!

Full Pseudocode

LPE(graph G):
  Compute in-degree for all gates
  levelOf[gate] = 0 for all gates

  // Initialize queue with all source gates (in-degree = 0)
  for each gate g:
    if inDegree[g] == 0:
      Queue.push(g)
      levelOf[g] = 0

  while Queue not empty:
    u = Queue.pop()
    result_order.push(u)

    for each gate v that u connects to:
      inDegree[v] -= 1
      levelOf[v] = max(levelOf[v], levelOf[u] + 1)  ← KEY NEW STEP
      if inDegree[v] == 0:
        Queue.push(v)

  // Group into stages
  criticalPathLength = max(levelOf) + 1
  for each gate g:
    stages[levelOf[g]].push(g)

  parallelSpeedup = total_gates / criticalPathLength
  return stages, criticalPathLength, parallelSpeedup
Why This is Novel (What to Tell Teacher):
Kahn's 1962 paper gives only a flat linear ordering — it has NO concept of parallel stages or critical path. No surveyed paper addresses this for logic circuit evaluation. LPE is our original modification that adds maximum-depth propagation to Kahn's BFS, enabling parallel stage identification — a feature used in real EDA (Electronic Design Automation) timing analysis tools.

What LPE Outputs (from our simulator)

Stage 0 [Primary Inputs]:    A, B
Stage 1:                     XOR1, AND1    ← can run in parallel!
Stage 2 [Final Outputs]:     Sum, Carry    ← can run in parallel!

Critical Path Depth:  3 levels
Parallel Speedup:     ~2x faster than sequential

7. ⭐ Novel Algorithm 2 — Incremental Signal Propagation (ISP)

⭐ Original Contribution

Incremental Signal Propagation (ISP)

File: NovelAlgorithms.h | Menu Option: 16 | Complexity: O(D + E_D) where D ≪ V

What Problem Does ISP Solve?

Imagine you have a circuit with 1000 gates. You're using the web GUI — clicking input switches to toggle signals. Every time you click one switch, the naive simulator re-evaluates all 1000 gates from scratch. But if you toggled INPUT A, maybe only 50 gates downstream of A actually changed. The other 950 gates produce the same output as before — re-evaluating them is pure waste.

❌ Naive Approach (Before ISP) Re-evaluate ALL V gates every time ANY input changes.

Complexity: O(V + E)
For 1000 gates: always 1000 evaluations
✅ ISP Approach Only re-evaluate gates REACHABLE from the changed input (dirty gates).

Complexity: O(D + E_D) where D ≪ V
For 1000 gates: maybe only 50 evaluations

Simple Explanation (In Plain English)

Imagine a phone tree (chain of calls). If manager A calls manager B calls employees C, D, E. If A changes their message, only B, C, D, E need to be re-called — not the entire company. ISP finds exactly which gates are downstream of the changed input and only re-evaluates those.

How It Works — Step by Step

  • 1
    User toggles an input gate. Say INPUT A changes from 0 to 1. We mark A as "dirty" (needs re-evaluation). Create a BFS queue starting from gate A.
  • 2
    Dirty-bit BFS. From gate A, follow all outgoing wires. For each gate reachable from A — mark it dirty too. Continue BFS until no more reachable gates. All dirty gates = the "affected zone" of the circuit.
  • 3
    Topological filter. Take our pre-computed topological order. Filter it to keep only dirty gates, maintaining their relative order.
  • 4
    Re-evaluate only dirty gates. Run the signal propagation only on this filtered subset. Skip all gates that are NOT dirty — their outputs haven't changed.
  • 5
    Report efficiency. Show how many gates were skipped vs. how many were evaluated. This is the efficiency gain.

Example

Circuit with 6 gates: A(0), B(1), XOR(2), AND(3), Sum(4), Carry(5)
User toggles gate A (INPUT A):

Dirty-BFS from gate A:
  A → marks XOR, AND as dirty
  XOR → marks Sum as dirty
  AND → marks Carry as dirty

Dirty gates = {A, XOR, AND, Sum, Carry} = 5 gates
Non-dirty gates = {B} = 1 gate (skipped!)

Re-evaluate only: A → XOR → AND → Sum → Carry
Skip: B (its output didn't change)

For a larger circuit: toggling one input in a 1000-gate circuit
might only dirty 50 gates → 95% of computation saved!

Full Pseudocode

ISP(graph G, changed_gate c, topoOrder T):
  // Step 1: Dirty-bit BFS
  dirty[all gates] = false
  dirty[c] = true
  Queue.push(c)

  while Queue not empty:
    u = Queue.pop()
    for each gate v that u connects to:
      if not dirty[v]:
        dirty[v] = true
        Queue.push(v)

  // Step 2: Filter topological order to dirty only
  dirtyTopoOrder = []
  for each gate g in topoOrder T:
    if dirty[g]:
      dirtyTopoOrder.push(g)

  // Step 3: Re-evaluate only dirty gates
  for each gate g in dirtyTopoOrder:
    evaluateGate(g)   // reads current inputs, computes output

  // Step 4: Report efficiency
  D = count of dirty gates
  skipped = V - D
  percentSaved = (skipped / V) * 100
  return D, skipped, percentSaved
Why This is Novel (What to Tell Teacher):
All three surveyed papers (Kahn 1962, Tarjan DFS 1972, Tarjan DSU 1975) assume static, one-time computation on a fixed graph. None of them address what happens when inputs change dynamically during interactive simulation. ISP is our original algorithm specifically designed for interactive simulators where users toggle inputs in real time. This is the exact use case of our web GUI and CLI demos.

ISP Complexity Analysis

ScenarioGates EvaluatedComplexity
Naive (always full simulation)All V gates every timeO(V + E)
ISP (best case: isolated input)Only 1 gateO(1)
ISP (typical case)D gates where D ≪ VO(D + E_D)
ISP (worst case: input fans out everywhere)All V gatesO(V + E) = same as naive

In typical digital circuits, most inputs fan out to a small subset of the circuit → ISP is dramatically faster in practice.

11. Q&A Cheat Sheet — Answers for Teacher

What is the problem you are solving?
Physical circuit prototyping on breadboards is error-prone, slow, and expensive. We built a software simulator where any combinational digital circuit can be constructed, verified for correctness (cycle detection), evaluated (topological simulation), and exhaustively tested (truth table) — all instantly without any hardware.
Why did you use a directed graph to model the circuit?
A digital circuit is naturally a DAG — signal flows in one direction (input to output, no feedback allowed in combinational logic). Gates are vertices, wires are directed edges. This lets us use well-known graph algorithms like Kahn's BFS and Tarjan's DFS directly on the circuit structure.
Why Kahn's algorithm specifically? Why not DFS topological sort?
Both produce valid topological orders. We chose Kahn's BFS-based approach because it naturally processes gates level-by-level, which aligns with how real circuit evaluation works (wait for all inputs before evaluating a gate). It also made it natural to extend into our LPE novel algorithm. DFS topological sort processes in reverse post-order which is less intuitive for circuit simulation.
What is the novelty in your project?
We have two original algorithms. First, LPE (Levelized Parallel Evaluation): we modified Kahn's algorithm to propagate maximum path depth forward, grouping gates into parallel execution stages and computing the Critical Path Length. None of the 3 surveyed papers do this. Second, ISP (Incremental Signal Propagation): we designed a dirty-bit BFS that, when an input changes, re-evaluates ONLY the downstream-affected gates instead of all gates. This reduces complexity from O(V+E) to O(D + E_D). All surveyed papers assume static computation — none address dynamic re-simulation.
Can you explain LPE in simple terms?
Imagine a factory with shifts. Workers in the same shift don't depend on each other, so they work simultaneously. LPE organizes circuit gates into shifts (stages). Gates in the same stage are fully independent and can evaluate in parallel — like real hardware. The number of shifts needed is the Critical Path Length, a key metric in chip design.
Can you explain ISP in simple terms?
If only one input switch changes, why re-check every single gate in the circuit? ISP starts from the changed input and follows wires forward (BFS) to find only the gates that could possibly be affected (dirty gates). Then it re-evaluates only those, skipping everything else. Like a phone tree — only call the people downstream of the changed decision, not the whole company.
What is the time complexity of your simulation?
Full simulation: O(V + E) — same as Kahn's, where V = gates and E = wires. Truth table: O(2ᴺ × (V + E)) — run simulation for all 2ᴺ input combinations. LPE: O(V + E) — same as Kahn's, just with depth propagation added. ISP: O(D + E_D) where D is the number of dirty gates (D ≪ V typically).
How is DSU (Union-Find) used?
In a real circuit, multiple wire segments that are directly connected form one electrical "net" — they all carry the same voltage. DSU groups these connected wire segments into nets. When we need to know if two gates are connected, we check if they're in the same DSU set — O(α(n)) ≈ O(1) per query.
Why did you use adjacency list and not adjacency matrix?
Digital circuits are sparse — a gate typically has 2-3 inputs. An adjacency matrix would be V×V = potentially millions of cells for large circuits, most of them empty (zero). Adjacency list stores only actual connections, making BFS/DFS run in O(V+E) instead of O(V²).
What is the IEEE ISCAS '85 benchmark?
It's a set of standard test circuits published by the IEEE in 1985, used by chip designers worldwide to validate EDA simulation tools. We implement c17 — a 6-NAND circuit with 5 inputs — and verify our simulator produces the exact same 32-row truth table as the known specification. This validates that our algorithms are correct.
What are the limitations of your project?
1) Only handles combinational logic (no flip-flops or sequential circuits with memory). 2) Truth table is exponential (O(2ᴺ)) — not feasible for circuits with 30+ inputs. 3) Web GUI is a separate JS implementation, not directly calling C++ (due to browser sandbox). 4) No propagation delay modeling (gates are assumed to switch instantly).
What future work can be done?
1) Extend to sequential circuits (flip-flops, registers, state machines). 2) Add gate propagation delay modeling for timing simulation. 3) Compile ISP + LPE into WebAssembly to run C++ algorithms natively in browser. 4) Support BLIF/BENCH netlist file formats for importing standard benchmark circuits. 5) Implement formal verification using BDDs (Binary Decision Diagrams).
